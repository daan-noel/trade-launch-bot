# Strategies — TPSL snipers

File-level map of `backend/src/strategies/`. Two **intentional clones**: `tpsl_sniper_1` (canonical/live) and `tpsl_sniper_2` (clone + cohort scalp gates). A fix in one usually belongs in both.
Logic explainers: `@project_plans/tpsl-strategy/*`.

**Backtesting / param sweeps are strategy-agnostic.** The sweep engine, grouping,
aggregate, persistence, API, and page in `backend/src/sweep/` only see a
`Strategy`/`ParamSpace` impl returning a `TokenOutcome` — they never know which
strategy ran. TPSL2's impl (`sweep/strategies/tpsl2.rs`) reuses the *same* live
`entry`/`exit` pure fns below, so backtest and live resolve identical decisions. A
new strategy adds only its `Strategy`+`ParamSpace`+`AxesSpec` impl, a `registry.rs`
arm (its DB table triple + dispatch), and a migration — see [sweep.md](sweep.md).

## Dispatch — `runner.rs`

`StrategyRunner` (`new`, `run`) consumes `strategy_rx` in a `select!` loop and routes to both strategy services:

- `on_token_created(mint)` → entry gating + **inline** cap/holding-index claim → **spawn** DB insert + buy.
- `on_trade_executed(mint)` → exit evaluation → spawn sell.
- 1s clock tick → `sweep_time_exits()` (deadline exits that come due in silence). Const `TIME_EXIT_SWEEP_INTERVAL = 1s`.

The single `select!` loop **serializes** all position transitions across both strategies (no Holding→ExitPending interleave on the same position). To keep that serialization without head-of-line-blocking the loop on a DB round-trip, both sides do the **in-memory** transition inline on the select task and **spawn** the slow DB/chain work: an exit marks ExitPending + syncs the holding index inline then spawns the sell (`trigger_real_exit`); an entry claims the cap slot + holding-index entry inline (`sync_position(None, …)`) then spawns the insert + buy/fill, rolling the claim back (`remove_position`) if the insert fails. The inline count bump is what makes a launch-wave burst respect caps — the next ping sees the token against the cap before its insert's DB RTT completes. A just-claimed 0-entry position is gated out of every exit path (`clock_entry_time` ⇒ None), so it never mis-exits before its fill lands.

## Shared — `sim_progress.rs`

`SimProgress` (`new`, `start`, `tick`) — per-backtest progress reporter shared by both snipers' `backtest.rs`. Counts completed candidate futures atomically and broadcasts throttled `SseEvent::SimulationProgress { rule_id, processed, total }` (~100 frames/run + a final `processed == total`). The dashboard's `SimProgressBar` subscribes via `simulation_progress` SSE for a determinate bar.

**Cancellation:** `run_backtest` takes a `cancel: Arc<AtomicBool>` it polls per fetch chunk (skips the chunk + ticks its candidates so the bar still completes) and once after the collect (bails with `"simulation cancelled"`). The simulate handler registers the flag in `AppState.sim_cancels` (keyed by `rule_id`, removed via RAII guard on every exit path); `POST /strategies/tpsl{1,2}/rules/{id}/simulate/cancel` flips it. A cancel surfaces to the client as `{cancelled:true}` (HTTP 200), not an error.

`tpsl_sniper_2/` adds `cohort.rs` (launch-cohort primitive) and `entry/scalp.rs` (cohort-based scalp entry gates). `find_scalp_entry` runs in **one O(n) forward pass** — the launch cohort is fixed by the slice's first trade, so cohort/outside flows, the trailing alive-window sum, last-seen real reserves, and the higher-low confirmation index (`higher_low_confirmed_index`, a single forward pass with **no** intermediate `series` Vec) are carried forward instead of recomputing `scalp_features` per candidate (was O(n²)). `scalp_features` / `higher_low_confirmed` / `cohort::held_ratio` / `cohort::outside_net_sol` are retained as the per-prefix oracles the linearized path is tested against.

**`TradeRow` generic (shared with the sweep).** The trade-walking fns in both clones — `find_scalp_entry` (and its caller-supplied-cohort core `find_scalp_entry_with_cohort` + the `scalp_cohort` helper the sweep hoists per-token), `find_worst_case_paper_entry`, `find_entry_fill_in_trades`, `find_trade_driven_exit` (+ the sweep's caller-cohort `find_trade_driven_exit_with_cohort`), `ExitWalkState`, `ladder_reason`, and the `cohort::*` primitives — are generic over the `TradeRow` trait (`models/trade.rs`) rather than hard-typed to `&[Trade]`. The live path passes the cache's slim `CachedTrade` projection (`Wallet = u32`, wallet-interned per token — Phase B step 2) and monomorphizes; the backtest passes full `&[Trade]` (`Wallet = String`); the param sweep passes its wallet-interned `SweepTrade` projection (`Wallet = u32`) — see [sweep.md](sweep.md). One implementation, so decision parity holds across live/backtest/sweep, and live cohort-set membership is integer-keyed like the sweep's. `CachedExitState` (the live incremental memo) is **generic over the wallet type** (`CachedExitState<W = u32>` in tpsl2, so its E5 cohort set is `HashSet<u32>` for the live `CachedTrade` and `HashSet<String>` for the `Trade`-driven unit tests; tpsl1's memo has no cohort, so it stays `<T: TradeRow>`) and folds the cache's `CachedTrade` slice directly — no full `Trade` is retained in memory. (The "fix-in-both-clones" rule still applies — and both are now generic.)

**tpsl2 target (trigger-trade) capture.** At position creation (fingerprint match) `Position::new` stores only identity fields (`mint`, `wallet`, `strategy`, `rule_id`) — all `target_*` and `entry_*` fields start empty (`None`/`0.0`/`""`). They are filled in two independent writes: `update_target` when the scalp trigger fires, `update_entry` when the actual fill lands. **Amounts are stored as TOKEN counts** (`target_token_amount`/`entry_token_amount`/`exit_token_amount`), never SOL — SOL is derived at display as `price × tokens` (#4). The scalp-entry signal trade is the *target*; `EntryFill` carries its `amount_tokens` so it can be persisted. Real: `await_scalp_entry_signal` returns the qualifying `EntryFill`; `service.rs` writes it via `position_repo.update_target` **before** sending the buy, then the wallet's own on-chain fill fills `entry_*` independently (a true gap) via `adopt_existing_fill_if_present` (`entry_token_amount` = `fill.token_amount`, the on-chain sell quantity — unchanged). Since the trigger comes off the sig-free live cache (Phase B step 1), the persisted real `target_tx` is empty — `target_*` is a display/diagnostic snapshot, not a decision input, and re-fetching the trigger's real sig would add a DB round trip to the entry path. Paper: `spawn_entry_fill_poll` resolves the trigger **index** (`find_scalp_entry_with_cohort_indexed`), writes the trigger via `update_target` (`target_token_amount` = the trigger trade's own token count), then records `entry_*` from `entry/scalp.rs::find_worst_case_paper_entry_at` (index-keyed) — the highest-priced (worst-case) trade in the trigger's slot S or S+1, strictly after it, non-dust/priced; ties → latest; empty → the trigger itself. The paper `entry_token_amount` is the **position size in tokens** = `buy_amount / entry_price` (guarded `entry_price > 0`), written by `update_entry` (the worst-case fill supplies only entry tx/price/time; its own `amount_tokens` is not used for sizing); the full-bag `exit_token_amount` is the `entry_token_amount`. **Backtest** mirrors this same trigger→worst-case-fill pair (see `backtest.rs` above), so a tpsl2 simulation reproduces the live target↔entry slippage gap; the **paper-test-run** view surfaces the stored `target_*` straight off the `Position` via `paper_position_to_sim_result`. The gap vs. `entry_*` is derived client-side, not stored.

## Exit ladder (priority order)

`LiquidityExit → StopLoss → TakeProfit → TrailingStop → Stall → TimeStop`.

- Trade-driven (`find_trade_driven_exit`, each new trade) **and** clock-driven (`find_clock_driven_exit`/`should_position_exit_on_clock`, 1s sweep, Stall/TimeStop only) share feature predicates so they never drift. Both clock fns take a `&LadderParams` (the resolved scalars), not a `&Rule` — so the sweep gate never deep-clones a rule.
- Optional features (0/None = off): `p_exit_trailing_stop_pct` (E1), `p_exit_time_stop_secs` (E2), `p_exit_stall_secs` (E3), `p_exit_liquidity_drop_pct` (E4), `p_exit_cohort_ratio` (E5, tpsl2). TakeProfit + StopLoss always on.
- **Percent convention (all `p_*_pct` / ratio params + `tolerance_pct`):** stored whole-percent and divided by 100 at the comparison site. Take Profit is unbounded above (`> 0`); every other percent is clamped `0–100` (server-side `validate_percent_ranges`, also enforced by the form `min/max`). The two cohort params (`p_entry_max_cohort_held`, `p_exit_cohort_ratio`) were once raw fractions (`0.30`/`0.05`) and were rescaled ×100 to whole-percent (the data-only rescale migration has since been folded into the squashed `0001_init.sql`). So `held_ratio > p_entry_max_cohort_held/100` and `net <= bought * p_exit_cohort_ratio/100`.

## Real vs paper

- `rule.trade_mode` selects path; same service, branches at execute. Real counters are all-time; paper counters are scoped to the current run.
- Entry recorded only from an **indexed** trade (no synthetic create-time fill), real and paper alike.

## Invariants (preserve when editing)

1. No double-buy — only a confirmed on-chain revert (`classify_silent_send`) re-sends.
2. No double-sell — the runtime cache's `exiting` guard gates in-flight sells across **all** exit paths (trade/time ladder, paper fill-poll, and the manual Stop&Close lifecycle), so they can't race the same position into two sells. `try_begin_exit` returns a RAII `ExitGuard` held for the exit's lifetime; dropping it (normal return OR a spawned-task panic) frees the slot, so a panicked sell can't wedge the position in `exiting` forever (1A-1). A position left stranded in `ExitPending` (panic, or a process crash+restart — the holding cache only loads `Holding`) is re-driven by `redrive_orphaned_exit_pending` (1A-2 boot / 1A-4 in-process reaper); the atomic guard claim prevents re-driving an exit that's still in flight.
3. Sell-confirm via the `trades` feed, **no new RPC poll**; poll the full window before concluding a retry (see CLAUDE.md "Gotchas" — naively flipping confirm off fires duplicate sells). The confirm loop registers its `TradeSignals` guard once per exit and re-runs the `net_token_amount_by_wallet_and_mint` aggregate **only when the guard's `seq` advanced** (a new trade landed for this wallet+mint); bare fallback ticks skip the scan. The aggregate is additionally **rate-limited to once per `SELL_BALANCE_QUERY_MIN_INTERVAL_MS`** (250 ms, below the 500 ms poll interval) so a dump that bumps `seq` per landed leg coalesces many notify-driven wakeups into one SUM — and that floor is **bypassed at the poll deadline**, so a clear that landed during a coalesced burst is always confirmed before any (wasteful, double-sell-risking) retry. SQL stays the authoritative "cleared" gate (deduped by PK) — don't replace it with a pure in-memory balance: feed redelivery would double-count and over-sell.
4. Time exits fire on silence (1s sweep).
5. Strategy eval reads `runtime_cache.rs` only — never queries DB per trade event.
6. Live-rule edit guard — `update_tpsl_rule` (api/handlers/strategies/tpsl{1,2}.rs) rejects (`409`) any change to frozen fields while a rule is *live* (`is_active || holding_count_by_rule > 0`): the match/entry/exit criteria + tolerance (`touches_frozen_fields`) **and** `trade_mode` (checked by value, since the PUT always carries it). Only `rule_name` + the hot sizing fields (`buy_amount`, `p_max_concurrent_tokens`, `p_max_total_tokens`) may change mid-run — everything else redefines the rule. Mirrors the per-group lock in `RuleFormModal` (which also disables the Mode select while live and resets every group lock to *locked* on each open, so an unlock never carries across edits); the PUT still `reload_rules` so hot edits propagate to the runtime cache.
7. Clear-results guard — `clear_paper_result_tpsl_rule` (`DELETE …/paper-result`) wipes a rule's paper run history via `paper_repo.clear_runs` (CASCADE positions). Paper-only (`400` otherwise) and idle-only — rejects (`409`) a *live* rule so an in-flight run is never deleted under itself. The frontend "🗑 Clear results" button (in the Paper Test result header) is disabled for live rules and confirms inline; on success it drops the `StrategyPaper` cache tag (`invalidatePaperResult`) and refreshes the rule list so lifecycle reads *Idle*. **Real position history is never cleared by this path.** Separately, the row **Duplicate** (⧉) action opens `RuleFormModal` in *create* mode pre-filled from the source rule (name suffixed " (copy)"), so a copy saves as a new rule via the create endpoint — no backend change.
